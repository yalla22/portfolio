Overview

One tool, two flight-controller worlds

Drone crash investigation usually means manually plotting huge binary logs for hours. Different flight controllers use different — and sometimes encrypted — formats. This tool auto-detects the format, normalizes it, and produces a consistent, color-coded diagnosis in seconds.

header == 0x00 0xFF
→ JIYI binary (plaintext) — convert → parse
header == 0x37 0xC8
→ JIYI binary (XOR-encrypted) — decrypt → convert → parse
JIYI XOR Decryption

Reverse-engineering the cipher

JIYI obfuscates its SD-card logs with a single-byte XOR cipher (key 0x37). The giveaway: the encrypted header XORs cleanly into the known plaintext message marker.

Encrypted header0x370xC8
XOR key⊕0x370x37
Decrypted (= JIYI marker)=0x000xFF
0x37 ⊕ 0x37 = 0x00 · 0xC8 ⊕ 0x37 = 0xFF → the known JIYI header 0x00 0xFF. Confirmed: the whole file is XOR'd with 0x37.
def _xor_decrypt(src, dst, key=0x37):
    data = src.read_bytes()
    dst.write_bytes(bytes(b ^ key for b in data))
Self-Describing Binary Parser

Schema first, then data

Both binary formats begin messages with FMT records (type 0x80) that declare each message's name, format string, and column names. The parser reads that schema, then struct-decodes every record — applying unit scalars (e.g. lat/lng × 1e-7).

Step 1 — Schema

Read FMT (0x80) table

Message id → name, format chars, columns. A FORMAT_CHARS map turns each char into a struct code + byte size.

Step 2 — Decode

Unpack every record

Scan for message markers, decode by type, apply scalars & ASCII strings. Robustness: timestamp caps, range filters for corrupt values, median-not-last-value.

Challenges & Solutions

Engineering the hard parts

Problem

Encrypted JIYI logs

Solution

Identified a single-byte XOR (0x37) from the header, decrypt the file, then convert.

Problem

Windows-only .NET converter

Solution

Run binToLog.exe on Linux via mono inside a virtual display (xvfb-run) — fully headless in Docker.

Problem

Converter uses fixed filenames

Solution

An asyncio lock serializes conversions so concurrent uploads never collide. (Future: per-job temp dirs / queue.)

Problem

Corrupt / partial logs

Solution

Timestamp sanity caps, range filters for impossible values, and median-not-last-value so a corrupt end-of-log burst can't skew results.

How you investigate a log (say this out loud)

1
Context
Frame, firmware (MSG), mission, mode, flight phase.
2
What did it report?
Scan ERR / EV / MODE for the first anomaly + timestamp.
3
Control breakdown
ATT DesRoll vs Roll — when did actual stop following desired?
4
Work outward
Motors (RCOU) → sensors (VIBE, GPS, MAG, EKF) → power (BAT/POWR).
5
Root vs symptom
What happened first? e.g. voltage sag → motor can't hold → attitude diverges.
6
Report + CAPA
Findings + corrective & preventive actions for the fleet.
Golden line: "I always ask what happened first — the autopilot logs the symptom loudly, but the root cause is usually a few hundred milliseconds earlier in a different subsystem."

Anomaly Playbook

Symptom → signature → cause

Vibration

Signature: VIBE >30 (bad >60), clipping counters rising.

Effect: EKF pos/alt errors, flyaways.

Fix: balance props, soft-mount, harmonic notch filter.

GPS glitch / jamming

Signature: NSats drop, HDOP spike, position jumps, EKF pos innovations spike.

Effect: LOITER drift, GPS failsafe. Spoofing = confident-but-wrong position.

Compass interference

Signature: high variance, field scales with throttle/current.

Effect: toilet-bowling, yaw drift.

Fix: recalibrate, COMPASS_MOT, relocate compass.

Power / brownout

Signature: Volt sag under Curr spike; POWR.Vcc dip; abrupt log end.

Cause: sagging battery, weak BEC, loose connector.

ESC / motor failure

Signature: one RCOU channel persistently high to hold attitude; ESC RPM/temp anomaly.

Effect: attitude diverges → crash.

Tuning oscillation

Signature: actual chases desired with ringing; oscillating motor outputs.

Fix: Autotune; adjust rate PIDs / filters.

Cheat Sheet

Numbers to have cold

Vibration — <15 great · 15–30 OK · 30–60 concerning · >60 bad. Clipping should be 0.
GPS — HDOP <1 great, <2 OK; NSats ≥6 min, ≥10 good; Status 3=3D,5=RTK-float,6=RTK-fixed.
EKF variance (0–1) — <0.5 good · 0.5–0.8 marginal · >0.8 bad · ≥1.0 failsafe.
Board Vcc (POWR) — ~5.0 V; <4.5 V → brownout risk.
Battery (12S JIYI) — warn <44 V, critical <42 V.
RCOU — balanced ≈ similar; one persistently high = that arm's motor/ESC/prop.
Q&A Bank

Likely questions & crisp answers

How do you detect the log format?
Magic bytes: 0xA3 0x95 → ArduPilot; 0x00 0xFF / 0x37 0xC8 → JIYI binary; else text via >80% printable-byte sniff.
Walk me through the JIYI XOR decryption.
JIYI XORs logs with a single-byte key 0x37. The encrypted header 0x37 0xC8 XORs to 0x00 0xFF — the known plaintext marker — so I detect 0x37, XOR the whole file, then convert.
Why Mono and Xvfb?
binToLog.exe is a Windows .NET tool. Mono runs it on Linux; Xvfb gives it a virtual display so it runs headless in Docker.
Why the asyncio lock — how would you remove it?
The converter uses fixed filenames, so concurrent jobs would collide; the lock serializes them. Fix: per-job temp dirs or a conversion queue.
How do you parse a self-describing binary log?
Read the FMT (0x80) records that declare each message's fields, then struct-decode every record and apply unit scalars.
Copter is toilet-bowling in LOITER — cause?
Compass interference / bad calibration, or a GPS glitch. Check compass variance and field-vs-throttle, and GPS NSats/HDOP.
How do you spot a failing motor/ESC?
RCOU imbalance — one motor commanded persistently higher to hold attitude — plus ESC RPM/temp anomalies and matching vibration.
IMU hardware fault vs a real maneuver?
A hardware glitch is an instantaneous spike that snaps back the next sample; a maneuver is gradual. My detector flags the snap-back pattern.
Signs of a brownout?
Battery Volt drop under a current spike, POWR.Vcc dipping below ~4.5 V, and the log ending abruptly mid-flight.
Biggest weaknesses / what would you improve?
No automated tests, synchronous parsing, and the fixed-filename converter bottleneck. I'd add tests, per-job temp dirs, a job queue, and a labeled set to measure check precision.
